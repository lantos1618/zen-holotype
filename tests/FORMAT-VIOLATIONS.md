format" is the specification; every row below is a file that does not match it.

each one is reported, not fixed, so the owning author makes the change.

## The systemic ones

Rules that fired across a whole suite. Each is one decision, not N edits.

### `mf-bare-position` — 92 file(s), WARN

*position omits the path; TESTING.md writes path:line:col.* In: `must-fail/lex`, `must-fail/own`, `must-fail/parse`, `must-fail/sema`.

Amend `docs/TESTING.md` to say the path may be omitted for a single-file test, where it can only mean that file. Four suites independently chose the bare form, which is the tell that the spec asked for something nobody wanted to write. `tests/run.py` already resolves a bare `line:col` against the test's entry file, so blessing it costs nothing; the alternative is editing 92 files to add a redundant filename.

### `corpus-exit-zero` — 16 file(s), WARN

*.exit holds 0; TESTING.md says omit the file when it is 0.* In: `corpus/own`, `corpus/traps`.

Delete every `.exit` that holds `0`; an absent `.exit` already means 0. Keeping them is harmless to the runner and corrosive to the format: the next author copies the directory and now `.exit` looks required.

### `mf-merged-position` — 10 file(s), ERROR

*message and position merged on line 1; the position must be its own line.* In: `must-fail/modules`.

One suite wrote `path:line:col: message` on a single line. Split each into two lines. The runner cannot accept the merged form without also accepting a test that asserts a message and no position, which is exactly the assertion `TESTING.md` says decays fastest.

## Four of these need a spec decision, not an edit

`docs/TESTING.md` is authoritative, so where it is silent the fix is a
sentence there — not a convention invented in a suite.

1. **What a directory test's expectation is called.** The spec says a
   directory holds "its module tree plus `.expected` / `.exit` / `.stderr` at
   the directory root", which reads equally as a literal `.expected` and as
   `<name>.expected`. 22 tests chose the literal dotfile, one chose
   `<name>.expected`, and `tests/determinism/fixture` chose `main.expected`.
   The runner accepts all three; the spec should name one. A dotfile is
   invisible to `ls` and to some `git add` habits, which argues for
   `main.expected` — it also matches `main.zen`, already mandated.
2. **Whether a position may omit its path.** See `mf-bare-position` above.
3. **No way to bound the diagnostic count.** `TESTING.md` requires that "one
   syntax error must not cascade into fifty", and the format cannot express
   it: extra diagnostics are always allowed. `must-fail/parse` invented a
   `.count` file, which nothing reads. Either add a `.count` (or
   `.max-diagnostics`) to the format, or drop the requirement.
4. **What a `must-fail` test's compilation root is.** For a flat test the
   runner passes the `.zen` file; for a directory it passes the directory
   (`tests/corpus/codegen/README.md` assumes the same). The paths a
   diagnostic prints follow from that choice, and positions are asserted
   against them, so it belongs in the spec.

## What is deliberately not a violation

Recorded so nobody 'fixes' one of these:

- **Extra diagnostics beyond those asserted.** A `must-fail` test lists the
  positions that *must* appear; the compiler may report more. One ownership
  test legitimately produces two diagnostics.
- **An empty `.expected`.** The trap corpus prints nothing on stdout and
  carries its assertion in `.exit` and `.stderr`. That is a real assertion.
- **A `.stderr` on a corpus test.** It is a substring check, so a trap message
  can be asserted without pinning the whole stream.
- **Test names that do not match the source file they exercise.**
