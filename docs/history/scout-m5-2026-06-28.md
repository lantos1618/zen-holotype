# M5 re-scout — usability verdict + polish queue

## VERDICT
NOT at the ~7/10 "write a real program without a wall" bar. Four walls block the headline expressiveness pitch: HOFs are unusable unless made generic (F2), the `filter-map-reduce` pipeline silently miscompiles to `[void]` (F9), a closure-in-a-struct crashes the moment it crosses a function boundary (F1), and nested-generic `>>` won't parse in expression position (F6). The turbofish/closure checker is also wide open — undefined types reach C as raw identifiers (F13) and wrong-arity closures silently miscompile (F15). Effective bar today: ~5/10. Unblock F1+F2+F6+F9 (the four walls) and validate turbofish/closure args (F13–F15), and Zen clears 7/10.

## REGRESSIONS (fix first)

### R1 — Struct with a function-typed field cannot cross a function boundary (miscompile → ICE)
dimension CLOSURES/HOF · sev high · value high · REGRESSION · lane **compiler-core-serialized** (inliner + codegen member-access + checker arg-fit)
Repro:
```
F1a — inlined callee -> invalid generated C (internal compiler error). /tmp/m5-32.zen:
  { println } = std.text.fmt
  Box*: { v: i32, op: (i32) i32 }
  getv = (b: Box) i32 { b.v }
  main = () i32 { b := Box(v: 42, op: (n) { n + 1 })  println(getv(b))  0 }
Command: ./zenc run /tmp/m5-32.zen
Observed: "error: invalid type argument of '->' (have 'Box')" then "zenc: internal: generated C failed to compile (this is a compiler bug)". Emitted C declares the inlined param as a VALUE `Box __zen_local___zen_local_b = (Box)...` but accesses it as `__zen_local___zen_local_b->v` (pointer). Expected: prints 42. Note: removing the fn-typed field `op` (struct `{ v: i32, w: i32 }`, /tmp/m5-34.zen) makes the SAME code emit `.v` and print correctly (50) — so the fn-typed field is the trigger.

F1b — non-inlined callee -> checker rejects the argument. /tmp/m5-35.zen:
  Box*: { v: i32, op: (i32) i32 }
  sumv = (b: Box, n: i32) i32 { (n <= 0).match ({ true => 0, false => b.v + sumv(b, n - 1) }) }
  main = () i32 { b := Box(v: 7, op: (x){x+1})  println(sumv(b, 3))  0 }
Command: ./zenc run /tmp/m5-35.zen
Observed: "error[arg-type]: argument type does not fit the parameter" at `sumv(b, 3)`. Expected: prints 21. Also calling the field through a param (/tmp/m5-33.zen `b.op(b.v)`) gives "error[undefined-name]: undefined name" on `op`.
```
Fix-sketch: a struct with a fn-typed field is classified pointer-passed at the call/member ABI, but the inliner substitutes a by-value local and the checker's arg-fit disagrees. (1) In codegen pick `.` vs `->` from whether the receiver expression is actually a pointer, not from the field set; (2) in the checker accept a `Box` value where a `Box` param is expected and resolve `op`/`v` on the by-value struct. Diff emitted C of /tmp/m5-32.zen vs /tmp/m5-34.zen to find where `->` flips.

### R2 — iter.map silently miscompiles: output element type U defaults to void
dimension HOF pipeline / generic inference · sev high · value high · REGRESSION · lane **compiler-core-serialized** (check.zen infer_call; combine with P4/R-fix for the same U-from-closure-return root)
Repro:
```
./zenc run /tmp/m5-silent.zen where the file is:
  { println } = std.text.fmt
  heap = std.mem.heap
  { map, fold } = std.collections.iter
  main = () i32 {
    m := heap.gpa(); a := m.addr()
    xs: [i64] := [1, 2, 3, 4]
    ys := a.map(xs, (x: i64) i64 { x + 10 })
    println(fold(ys, 0, (acc: i64, x: i64) i64 { acc + x }))
    0
  }
Observed: prints 23. Expected: 50 ([11,12,13,14] summed). SILENT wrong answer. A second program (./zenc run /tmp/m5-mapdbg.zen) that loops/indexes the unannotated map result instead fails with an INTERNAL compiler error: `error: variable or field ... declared void` / `void value not ignored`. Adding the result annotation `ys: [i64] := a.map(...)` makes it print 50 correctly. Contrast: iter.filter (returns [T], T comes from xs) works unannotated (/tmp/m5-filterdbg.zen prints 2/4/6). The defect is specific to map's fresh U type param, which appears only in the closure return type `(T) U` and the result `[U]`: U is never unified with the lambda's DECLARED return type and defaults to void. This breaks the headline 'write a filter-map-reduce pipeline' use case — the same root made my earlier /tmp/m5-pipe2.zen evens→squares→sum print 56 instead of 220, undetected.
```
Fix-sketch: unify a type param that appears in a closure parameter's result position (`f: (T) U`) with the lambda's declared return type, exactly as `[T]` binds T. At minimum, when U is unresolved EMIT a need-annotation error — never silently lower to `[void]`.

### R5 — Wrong-arity / wrong-type closure to a HOF stdlib fn is silently accepted and miscompiles
dimension diagnostics · sev medium · value medium · REGRESSION (accepts-invalid → wrong result) · lane **compiler-core-serialized** (check.zen lambda↔fn-param binding)
Repro:
```
/tmp/m5-arity.zen:
{ fold } = std.collections.iter

### R6 — Float formatter prints garbage (`.0e-301`) for |x| < ~1e-292

### P2 — Non-generic HOF cannot call its concrete `(i32) i32` parameter (forces every HOF to be generic)
dimension CLOSURES/HOF · sev medium · value medium · lane **compiler-core-serialized** (checker fn-typed-param lowering/callable-bound)
Repro:
```

  inc = (n: i32) i32 { n + 1 }

### P5 — UFCS on stdlib free functions requires a name-import; a module alias is not enough, and the error is a dead end
dimension imports / UFCS ergonomics · sev medium · value medium · lane **compiler-core-serialized** (check.zen UFCS resolution + diagnostic)
Repro:
```
./zenc run /tmp/m5-alias4.zen (alias `iter = std.collections.iter`, then `xs.sort((p,q){p<q})`) → error[undefined-name] at `xs.sort` with hint 'declare the name, import it, or qualify the intended module binding'. Same for `xs.fold` / `a.filter` via an iter alias (/tmp/m5-alias3.zen). But the EXACT same UFCS shape works for modules in the implicit bootstrap closure: ./zenc run /tmp/m5-join-noimport.zen calls `a.join(parts, ",")` with std.text.str NOT imported at all and prints `a,b,c`; `a.integer_in(n)` likewise. So `a.join` (str) needs zero imports while `xs.fold` (iter) needs `{ fold } = std.collections.iter` — a module alias never enables UFCS. The hint tells the user to 'qualify the intended module binding', which is impossible for a receiver call like `xs.fold` (you cannot write `xs.iter.fold`). Real wall: a user who writes `iter = std.collections.iter` then `xs.fold(...)` gets a dead-end error.
```
Fix-sketch: either register a module-aliased import's exported functions for UFCS lookup, or special-case the diagnostic — when `recv.method(...)` resolves to a fn reachable only under an aliased/qualified module, say so and suggest the `{ method } = <module>` name-import (not 'qualify the binding').
